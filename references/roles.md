# 按用途分配配置与检测

使用前先确认“个人电脑 / 中转机”和“从零配置 / 检测”。设备型号不决定用途：Mac mini 可以是个人桌面，也可以是跳板、代理网关或应用运行主机。

## 首轮提问

用户未说明时，先问并等待答案，随后才采集电脑配置：

> 这台机器主要做什么：个人日常使用，还是中转/网关？这次要从零配置，还是检测现有环境中的泄露和配置遗漏？

可用两个选择题分别收集用途和模式。用户已经明确给出某项时不重复问；没有明确的项保持待答，不先按机型猜测。用户只说“检查一下 Mac mini”时，模式已知是检测，用途仍需确认。续接 RUN.md 已记录且用途未变时沿用。

用户按 [培训入口](member-onboarding.md) 明确选择“已有配置先检测并修复，没有配置从零准备”时，可只读核对配置来源来确定分支，沿用请求中写明的个人电脑用途；无法判断时只补问具体缺项。

中转机再确认一个必要问题：

> 它负责哪些工作：只做 SSH/frp 跳板、给其他设备转发上网流量，还是自己也运行 Claude／浏览器？可以同时承担多项。

同时明确下游设备范围和必须保留的管理入口；已有答案不再追问。兼用机器分别建立个人应用路径和转发路径，两条都验收。

## 个人电脑

目标是用户实际应用的环境一致：本机浏览器、Claude CLI、IDE/Desktop，以及实际使用的 WSL/容器/远端环境。

**从零配置：** 执行 B0～B6。优先本机显式代理试连，再接入所需系统代理/TUN；最后处理目标应用所在环境的时区、地区、语言和浏览器信息。没有需要就不创建跳板、共享代理或常驻网关服务。

**检测：** 执行 detection.md。逐应用比较实际出口与运行时特征，重点找系统代理与应用代理不同、NO_PROXY/PAC 例外、IPv6/UDP、浏览器 DoH/WebRTC、配置脚本重写，以及旧进程仍继承旧环境等遗漏。

collect_environment.py 适用于当前用户桌面/客户端基线；浏览器探针运行在真正使用的浏览器配置。SSH 远端执行的应用单独取证，不把笔记本设置代替远端结果。

## 中转机 / Mac mini / Mac Studio

先标记它实际承担的功能，可以多选：

| 功能 | 主要配置与检测 | 不能用什么代替验收 |
|---|---|---|
| SSH/frp 跳板 | 管理入口、到内网的路由、隧道维持与必要解析 | 跳板能登录不代表下游应用已有 JP 出口 |
| HTTP/SOCKS/VPN 或路由网关 | 下游接入方式、实际转发、DNS、IPv4/IPv6、UDP、最终出口和故障回退 | 中转机自己的 curl 成功不代表下游成功 |
| 机上运行 Claude/浏览器/任务 | 实际服务用户、进程代理/地区、登录会话与后台启动环境 | SSH 登录用户的环境不代表另一个用户的服务进程 |

纯转发机无需把系统 UI、键盘、字体、浏览器语言和时区改成日文。普通隧道转发不会替下游浏览器改写 navigator、Intl 或请求头；这些信息在运行浏览器的设备上检查。反向代理终止 HTTP/TLS 或机上实际运行应用时，再检查相应请求生成位置。

采集位置以功能为准。纯跳板/转发机优先用平台原生命令读取网络、服务与配置，不为完整桌面采集安装 Python，不读取无关用户的浏览器目录。机上确有应用时，在获授权的实际用户/进程上下文使用采集器和浏览器探针。

### 从零配置中转机

沿 B0～B6 执行，具体优先级为：保持管理通道 → 需要的内网 → 下游接入 → 预期最终出口 → 机上应用环境。

1. **确认接入方式。** SSH 本地转发、局域网代理、VPN 和作为路由网关是不同需求。仅做跳板时配置它所需的隧道和内网路径，不自动给所有下游开全局代理。
2. **确定运行用户与生命周期。** 日常用户登录时工作可使用其现有客户端；需要重启后无人登录仍可用的服务，在 macOS 用适合的 LaunchDaemon，在 Linux 用系统服务。记录已有 GUI 账号、SSH 账号、服务账号，不能默认相同。
3. **先验证出站。** 有 JP 出站需求时使用包内回环模板做 B3；此时 allow-lan:false 和回环绑定适合隔离测试。端口、握手、DNS、最终出口在中转机上先通过。仅跳板用途只验证其管理和内网链路，无需购买 JP 出口。
4. **再准备真实下游接入。** 若通过 SSH 隧道接入，可保留回环监听；若下游直接连接局域网代理，调整到用户指定接口/地址与所需允许范围，并配置该接入方式的认证。读取实际监听和连接来源。普通 TUN 开关不能证明 LAN 转发、系统转发/NAT 或下游 DNS 已配置。
5. **保护管理链。** 按 campus.md 准备 frp、当前 SSH、远程桌面及内网的独立路径。管理通道按约定直连属于预期，不因此判成目标业务泄漏。
6. **处理常驻需求。** 需要无人值守时读取电源/睡眠设置、服务启动用户与配置持久性；只调整会妨碍已确定用途的项目。不会为了普通个人电脑配置这套网关逻辑。
7. **实际下游验收。** 从至少一台每种获承诺接入方式的下游设备验证 HTTPS、DNS、必要的 IPv6/UDP 和最终出口，再核对中转机的连接记录。下游尚不可访问时记录“中转出站通过，下游未验证”，交用户具体测试步骤。
8. **恢复与故障。** 管理连接保持可达；出站故障时目标业务的行为满足预期。重启、退出 GUI 用户和断线演练仅在有授权维护窗口与恢复入口时执行。

[Apple launchd 说明](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html) 区分系统守护任务与登录用户任务；[Mihomo 通用配置](https://wiki.metacubex.one/en/config/general/) 定义 LAN 监听、允许地址及代理认证。以正在使用的版本和实际监听为准。

### 检测中转机

检查三类链路，分别给证据：

~~~text
管理：管理端 → frp/SSH/远程桌面 → 中转机 → 必要内网
转发：下游设备 → 中转机接入 → [中转入口] → 最终出口 → 目标服务
机上应用（实际存在时）：服务用户/应用进程 → 本机代理 → 最终出口
~~~

重点查下游是否绕过中转、默认路由/DNS 是否只对本机生效、IPv6/UDP 是否另走路径、例外规则是否过宽、入口与最终出口是否串反、GUI 和后台进程是否使用不同配置，以及代理失效后的回退。对外监听也核对是否超出了用户指定接入范围。

配置中的回退、启动依赖或路由缺口可以作为有证据的风险报告；没有实际运行证据时，不把“可能发生”写成“已经泄漏”。只读检测不切断隧道、不修改路由、不重启后台服务，也不要求用户为检测退出桌面。
