# 检测模式：发现未注意到的泄露与配置遗漏

先完成 roles.md 的用途确认。检测覆盖用户实际使用的应用和链路，目的是发现目标业务的意外出口、解析/协议旁路，以及可观察地区信息之间的差异。

默认只读：读取配置与运行状态、发起必要的短查询、执行临时浏览器探针、保存脱敏报告。检测不进入资源采购、软件安装、配置导入、活动组切换、系统代理/TUN 调整、故障演练或服务重启。用户已明确要求“检测并修复”时，先完成取证和问题说明，再修复已确认项目，沿用授权，无需再次逐项征求同意。

## D0 · 明确预期与位置

记录用途、模式、预期最终出口类型/国家、需要覆盖的应用或下游设备，以及特意直连的管理/校园业务。已有日本出口但地区目标没另说时沿用 JP；住宅、VPS 与中转入口分别标明。

从实际应用位置开始画路径。对于下游经 Mac mini 上网的场景，分别记录客户端、Mac、最终出口；对于 SSH 登录远端运行 Claude，应用位置在远端。无法访问的设备留待验证，不拿工具后端或代理检测进程替代。

## D1 · 同时看持久配置和运行结果

按 surfaces.md 与角色选择适用项，读取配置来源、GUI 扩展、生成配置、运行状态与实际连接。使用已有工具；无 Python/MCP 时用原生命令和实际配置完成可做部分。

个人电脑或中转机上实际运行应用的用户，可执行：

~~~text
python <skill-dir>/scripts/collect_environment.py --project-dir <实际项目> --output <work-dir>/baseline.json
python <skill-dir>/scripts/collect_environment.py --network --output <work-dir>/network.json
~~~

纯转发机改用 platforms.md 的网络/服务命令。采集器输出只是该进程的证据，不能代替全部应用或下游。

重点寻找已启用路径中的遗漏：

| 现象或路径 | 检测动作 | 结论依据 |
|---|---|---|
| 普通 IP 检测显示 JP，但应用仍有差异 | 对照应用进程、真实目标域名与连接链 | 是否确实覆盖目标连接 |
| 多套代理设置并存 | 对照系统/PAC、大小写环境变量、NO_PROXY、应用设置及 TUN 排除 | 实际应用选中的路径 |
| HTTP 正常，其他协议未知 | 分别测实际 IPv6、DNS/DoH、WebRTC/UDP/QUIC | 不能把 HTTP 成功外推 |
| 原配置正确，运行结果变化 | 读取配置脚本、扩展、生成 YAML 与组选择 | 是否被重写或命中更早规则 |
| 地区信息不一致 | 在实际运行应用的位置对照时区 ID/偏移、Intl、语言和请求头 | 哪个上下文仍保留差异 |
| 中转机能通，下游未确认 | 从获授权下游走其真实接入方式测同类目标 | 是否绕行、解析或转发缺口 |
| 管理连接/校园内网直连 | 与用户确认的例外和实际命中对照 | 预期例外不算泄漏 |
| 重启、掉线后可能变化 | 读持久配置、启动任务、既有故障日志与回退组 | 风险与实际发生分开报告 |

有 controller 时只用读取接口；避免输出连接内的凭据、完整 URL 和请求头。发现一条意外路径后检查同一规则影响的相关应用，不扫描其他人的设备或私人文件。

## D2 · 定向验证疑点

每个测试写明“哪个信号、在哪个设备/进程、什么结果会改变判断”。未知项目不为凑齐清单强行通过。

- 网络查询通过现有路径发起，记录来源、时间和应用。显式代理对照仅使用已知监听端口，并注明它与默认应用路径的区别。代理白名单和故障回退只读核对；不为对照关闭 VPN。
- DNS 地址属于哪个国家不等于 DNS 已泄漏；核对它用于 bootstrap、校园例外还是目标应用解析。没有递归出口实测时保留未验证。
- WebRTC 中私网、mDNS 和保留地址不等于真实公网旁路。只有与 HTTP 出口不同的公网候选且路径证据支持时，才描述具体的意外暴露。
- 浏览器使用 scripts/browser_probe.js 在实际配置执行。默认本地信息、两家出口和一次 STUN；{network:false,webrtc:false} 只测本地。探针不请求定位坐标，不用覆盖时区/语言的自动化配置充当用户浏览器证据。
- 检查目标站点已有定位权限、浏览器扩展和实际 Accept-Language；不为了检测授予定位、清站点数据或重新登录。
- 纯转发机的中文系统、非日本时区、字体不直接构成下游地区泄露；检查下游实际浏览器，或中转机上确实生成请求的应用。
- 读取回退组和现存故障记录可以指出可能直连；检测模式不主动停代理、撤防火墙或断管理连接。若需要演练才能确定，报告安排条件。

普通查询失败后先解释失败属于哪个测量条件，不连续重试。仅在修改了测试条件或得到新证据时再测。

## D3 · 报告与后续处理

先写已证实的问题，再写有依据的疑点和未覆盖范围。每项给“设备/进程 → 信号或连接 → 证据 → 实际影响 → 建议动作”。不要只列系统参数或一个风险总分。

| 状态 | 使用条件 |
|---|---|
| 已证实泄露/旁路 | 实际请求或运行时证据说明目标业务暴露了预期外的信息/出口 |
| 已确认配置差异 | 当前生效设置与目标不一致，但不自动声称平台已看到 |
| 有依据的疑点 | 规则或运行结构存在旁路条件，尚缺实际触发证据 |
| 符合预期 | 本次适用路径已有相应实测 |
| 未验证 | 缺设备权限、工具、维护窗口或测量条件 |
| 不适用 | 该用途不存在此应用或路径，并说明原因 |

示例：发现 NO_PROXY 命中目标域名，记录配置差异并核对实际进程；实际请求仍被 TUN 捕获并走 JP 时，不报告公网直连。发现回退组含 DIRECT，报告相应失效风险；没有触发证据就不说已经泄露。

报告应写明已测范围与未验证项目，结论只覆盖实际观察到的应用和路径。一个 IP 检测站通过不能覆盖全部应用和转发路径。

仅检测时交付报告和具体修复建议，到此结束。用户明确要修复或继续要求修复时，读取原报告、保存涉及配置的原值，执行最小相关改动并复测；缺资源按 B2 暂停，不把检测变成从头部署。
